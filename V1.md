# SORA — V1

**V1 is a usable product, not a development build.** The GUI is set up and the local model is in
control, so the owner can talk to SORA and she can talk, move and indicate back. As a companion
she is roughly at N.E.K.O's level, but with vision and audio that actually work and with
functional agent colleagues.

Governed by [VISION.md](VISION.md). Agreed by the owner on 2026-10-05; written by Opus 5.5.
**V1 is done when the acceptance test below passes on the owner's machine with the real model.**
Component tests, fixtures and screenshots do not count as passing it.

## Acceptance test

Run on the owner's machine with the real local model, real microphone and speakers, both
monitors, and no fixtures. Each step passes only if it is observed working.

1. **Launch.** One normal launch, with no flags or QA paths. SORA appears on the desktop with no
   application window. Launching again does not start a second SORA.
2. **Talk by text.** Open Chat and type a message. She replies in text **and out loud**, with her
   mouth moving, within a few seconds.
3. **Talk by voice.** Speak to her without touching the keyboard. She hears you, answers out loud,
   and the exchange appears in Chat. Interrupting her while she speaks stops her.
4. **Screen awareness.** With some app open, ask "what am I looking at?" by text, then again by
   voice. She describes the actual screen.
5. **Move and indicate.** Ask her to wave or sit, and she does. Ask her to go over to a window
   you name, and she walks to the ground beneath it, on either monitor. Ask her to run to the
   other side of the screen and wave, and she runs there, then waves. Ask her to look at or point
   to a control in a window, and she indicates the right one.
6. **Delegate.** Ask for something hard, for example a code question in a real project. She says
   who she is handing it to (Cody, Hermes, Aggie or Claude), keeps chatting while it runs, then
   reports the result in her own words. Asking her to cancel it works. A spoken agent name works
   too.
7. **Custom agent.** A custom endpoint added in Settings, with a port, default model, description
   and nickname, can be delegated to by its nickname.
8. **Settings.** Change the model or voice settings in Settings, save, and the change takes
   effect. It is still set after a restart.
9. **Memory.** Tell her something about yourself. Quit SORA completely, relaunch, and ask about
   it. She remembers.
10. **Failure.** Stop the model or an agent mid-task. She says something is wrong rather than
    freezing or inventing an answer, and recovers when it is back.

## How to run the acceptance test

Day-to-day usage is in [HOW_TO_USE.md](HOW_TO_USE.md). Everything that can be built or checked
without you is done. The steps above need your real microphone, speakers, monitors and model.
Before starting:

1. **Free the GPU.** Unload LM Studio's model (it used about 10 of the 16 GB), so SORA's brain
   gets the card. Hermes' own model server can stay if Hermes is in the test.
2. **Pull and launch:** `git pull`, then `.\Start-SORA.ps1`. It now opens the native app.
3. **In Settings → Models → Brain (local model):** click **…** beside **Brain model file (GGUF)**
   and choose `Models\Unsloth\gemma-4-E4B-it-Q4_K_M-GGUF\gemma-4-E4B-it-Q4_K_M.gguf`. Its
   projector `mmproj-F16.gguf` sits beside it and should be found automatically. Save, then
   **Reload model**.
4. **In Settings → Vision:** set the perception mode to **image-on-prompt**. Your saved settings predate
   the new default, so this one is a manual switch.
5. **Agents:** Claude, Cody, Aggie and Hermes are found automatically when installed. To test
   step 7, enable a custom agent in Settings (for example LM Studio's server on port 1234 with a
   loaded model, nickname "Pip"), then restart SORA.
6. Run steps 1–10 in order. Note anything that fails, with what you said and what she did.

Two things to expect:
- When an agent finishes, fails or is cancelled, SORA now posts a short message in Chat. Her
  model phrases it, and the factual line underneath is Core's record.
- The current keyword router ignores negation. "Do not edit files" is read as a request to edit
  files, so a read-only project task can be refused. Phrase such requests positively for now.
  The decision layer (after V1) replaces this router.

Close V1 with a dated record of the run in `docs/verification/`, under the name of whoever
observed it.

## Ground rules for V1 work

- Work on the **acceptance test, not on stages**. Before starting a task, say which test step it
  moves forward. Anything that moves none of them waits until after V1.
- **Only the native app** (`clients/desktop_shell`, possibly with several windows) gets work. The
  full app, widget and PWA are frozen: they stay and keep building, but get no features and
  have no parity gate (owner decision, 2026-10-05).
- Record each V1 slice in a changelog under the model's own name, as usual. Close V1 only with a
  dated record of the full acceptance test, observed on the owner's machine.
