## Ownership, timing and availability

`SoraRuntime` owns exactly one `AutomationWorker`. It starts after canonical initialization, existing interrupted-run reconciliation and the existing pending-run queue handoff. No dialogue model, window, desktop observation or client connection is needed to keep time. Normal Core cleanup fences and waits for the scheduler before draining existing task workers. Accepted managed shutdown synchronously fences scheduler admission before the HTTP acknowledgement cleanup signal. Repeated cleanup, including an already-cancelled worker, is safe.

Default loop interval is one second; each tick scans at most 32 pending occurrences and 32 active definitions. The supported test/internal configuration caps batches at 64 and intervals at 60 seconds. Ordinal continuation prevents scanning the entire store or repeatedly starving later rows. A five-second soft work budget limits starting more per-record operations; provider/admission waiting has a two-second deadline, with the deadline rechecked inside SQL. This is not a promise that SQLite I/O or settling an already-started transaction finishes in exactly five seconds. Cleanup waits five seconds before cancelling its loop; cancellation settles an already-started task admission rather than claiming a rollback that did not occur.

Current list/detail projections report actual loop state: `unavailable`, `running`, `degraded`, `stopping` or `stopped`. A saved acknowledgement retains the state observed at that historical save. Fetch list/detail for current availability; a receipt saying running is not proof the worker still runs, nor provider entitlement/task success. Older receipts with unavailable remain valid. A per-record corrupt projection is redacted and marks that tick degraded; the loop survives unexpected exceptions without publishing their private text.

## Reservation and atomic admission

Scheduling reuses the canonical reservation, anchored next-slot advancement and pure timezone/missed/overlap decisions. It does not enumerate a backlog. Each occurrence retains its definition version, behavior snapshot and deterministic submission key. The task guard rechecks current scoped definition/version/state/behavior, no other reserved/admitted/unknown overlap, and no already-committed submission for the key inside the existing task transaction. Pause/edit/delete before admission therefore rejects the old reservation; a separately admitted task remains active and needs its existing task Cancel.

The trusted Core dispatcher enters owner-local scope. Existing task routing, project/workspace selection, model/effort validation and static policy remain authoritative; no new agent runtime, generic shell/file writer, caller authority or recurring permission prompt. Static delegation/provider switches and delegation epoch are rechecked inside admission, including the actually selected provider after routing. Unsupported/disabled selections become a visible blocked occurrence rather than scheduler fallback/retry. Existing explicit `auto` task routing retains its documented routing behavior; an explicit provider/model is not silently substituted.

Task, original run, canonical submission, occurrence linkage and content-free revision/event/outbox changes commit in one SQL transaction. Failure publishing the occurrence event rolls back the task/run/submission too. Once this transaction starts, a cancelled awaiting scheduler settles its result and queues a genuinely created task exactly once. Queue handoff precedes optional post-admission trace work, so a later trace failure cannot strand that task. Admission before a shutdown fence is existing admitted work, not a promise of cancellation; admission whose guard sees the fence is rejected. Concurrent ticks are serialized and canonical uniqueness remains the durable deduplication boundary.

## Recovery and outcome meaning

Before attempting an unadmitted reservation, inspect its exact submission key. Existing submission evidence is linked/reconciled, never resubmitted or re-enqueued by the scheduler. The existing Core startup is responsible for previously pending task runs. Scoped owner/project, creator message/intent, SQL/body consistency and the original attempt-one run are validated. An owner's later task retry does not rewrite the original occurrence's run ID.

Unsubmitted stale-definition reservations are blocked. Recovered and long-delayed live reservations obey the same bounded missed-run policy; default Skip, optional bounded Run once. A wall-clock rollback leaves a future reservation waiting, with a second due check at SQL admission. Reserved/admitted/unknown work blocks overlap. No automatic retry, external-effect replay or exactly-once external-effect guarantee is introduced.

Reconciliation labels admitted work using actual canonical task/run/result evidence. Completed requires the original matching completed task/run and a matching stored validated completed result. Status alone or a missing result yields Unknown. Interrupted/uncertain/replaced runs and **normalized Unknown outcomes, even if the run status is failed**, remain Unknown and block overlap. Definite failed/cancelled runs are recorded as failed with a distinct canonical reason; cancellation is not mislabelled completion. Provider completion is a validated provider report, not independent proof of every reported external action. Events contain IDs/version/origin/status/reason, never the private behavior or provider error text.
