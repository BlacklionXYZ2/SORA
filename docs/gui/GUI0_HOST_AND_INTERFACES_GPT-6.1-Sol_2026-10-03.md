The channel is not a generic stop/adoption API for external Core and does not replace the remaining ownership requirements below.

Production GUI-1 uses a windowless `ApplicationContext`. It owns one tray/menu/shortcut registration, one connection coordinator and at most one instance of each primary panel. Chat form Close becomes Hide, not process or Core shutdown. Compact/expanded Chat share the same presenter, draft and request identity. Secondary windows use the same connection and retained legacy workflows. Ordinary boot need not open a persistent frame, start the microphone or require a working model/avatar.

Profile identity derives from the **resolved state-root path**, not the listening port, current directory or model name. Use a stable digest of the normalised Windows path plus the current user's security identity for local mutex/IPC names; record the version of the identity rule. Resolve links where supported and reject ambiguous identity rather than merging profiles. Isolated QA profiles therefore have distinct hosts even when launched from the same checkout.

The first host holds a profile-scoped named mutex for its full lifetime. A later launch uses a bounded current-user-only local IPC request to summon a named panel on that host; it does not start Core/model/player first. Validate sender/profile/request shape and allow only bounded host commands (show panel, show recovery, focus user-requested panel), never arbitrary executable commands, URLs, tokens or settings patches. Host failures/timeouts are reported, not worked around by starting another owner for the same profile. Recover a stale mutex/descriptor only after verified owner termination; PID alone is insufficient without process start/instance identity.

### Core discovery, readiness and management

One versioned profile-local runtime descriptor identifies the profile, Core instance/epoch, loopback endpoint, private token-file path and explicit service ownership. Credentials remain solely in the existing private token mechanism, read into memory and redacted from diagnostics. The descriptor is a discovery hint, not proof of authority. Authenticate the API and compare profile/Core identity before attaching; if current projections lack that identity, add a minimal typed identity projection in GUI-1 rather than trusting an open port or a successful generic status response.

States are distinct: host starting / disconnected / connecting / Core connected / model down or reloading / renderer unavailable. Panel skeletons, Settings/recovery, diagnostics and placement reset open before initial API success. Backoff and cancellation are bounded; no UI-thread waits. Reconnection reloads token state and resyncs canonical projections before explicit effects. Retain labelled stale cache and user drafts; never replay Save, Reload, task creation, Stop or presentation effects automatically.

| Launch condition | Required behaviour |
|---|---|
| Existing host for this profile | Send summon request, exit secondary host; no Core/worker/player launch |
| Reachable authenticated same-profile external Core | Attach with `owns_core=false`; do not silently adopt or stop its children |
| Verified absent Core, managed ordinary launch | Start exactly one profile-owned Core through retained helper wiring; keep panels/recovery usable while waiting |
| Port occupied by unrelated/unknown listener | Show conflict/recovery; do not attach by port alone or auto-pick a new port and spawn a duplicate same-profile runtime |
| Core startup/model/configuration failure | Host stays available; diagnostic state and explicit owner recovery, no success banner or restart loop |
| Explicit compatibility Desktop/Widget/Browser mode | Keep current workflows available during parity migration; clearly document separate legacy ownership |

Launcher reconciliation is GUI-1 implementation work: `Start-SORA.ps1` currently waits for API readiness and auto-selects a new port when the default is occupied; `open-manual-test.ps1` requires an API/token before starting a GUI. Add an opt-in host path first, with host/singleton discovery before any managed launch. Preserve `StateRoot`, `Settings`, `LlamaConfig`, `NoAvatar`, `AvatarPath`, dialogue provider/model/endpoint, workspace/write repository and timeout options, plus observation/capture/press/type helpers in `start-manual-test.ps1` / `start-full-sora.ps1`. GUI-6 changes the ordinary default only after ownership and feature parity acceptance; no existing launcher was changed by this specification.

### Hide, voice, tasks and Quit

Hide changes panel visibility only. Stop response targets the active conversation nonce. Stop voice is an explicit voice action. Cancel task uses the selected canonical task ID. Quit closes the host and unregisters local resources, then gracefully stops only services it positively owns. Attached external Core and its services stay running. Present active task/microphone consequences before managed Quit; do not silently treat panel dismissal as task cancellation or worker termination.

Managed shutdown needs a typed owner-local lifecycle request/control channel and awaited completion, not process-name killing. A bounded timeout yields a visible failure and preserved ownership evidence. Any force termination is a separate explicit action with exact targets. Starting another Core after failed shutdown is forbidden until absence is established. Persisted tasks and future automation occurrences use their Core reconciliation rules; the UI cannot promise cancellation from process exit.

### Preference import and corrupt configuration recovery

Create one versioned UI-only store under the chosen profile. It contains logical panel bounds/monitor identity/DPI, compact mode, selected UI view, theme/text-size/reduced-motion, shortcut and technical-detail preferences. Keep canonical access/model/voice/agents out of it. Do not persist private Core records, tokens or competing effective settings there. Process-lifetime Chat drafts are required; any cross-restart draft persistence requires an explicit retention decision and storage protection, not incidental logging.

Import known `WidgetSettings` fields (anchor, monitor, expanded, quiet, topmost, technical detail and saved coordinates) and `FullAppPreferences` fields (selected tab and technical detail) once. Normalise/clamp obsolete monitor/physical-pixel positions to reachable logical placement. Preserve byte-identical original preference files and record source/version/import status. Do not let import overwrite later host edits. Unknown/corrupt legacy files produce diagnostics and safe UI-only defaults, not authority changes. Old widget topmost must not silently turn all new panels topmost; record the legacy preference and offer an explicit pin choice consistent with the roadmap.

Missing/corrupt canonical configuration stays owned by the existing typed AppSettings validation/recovery controller and startup owner. Online recovery uses supported Core routes/revisions. If Core cannot start, a dedicated owner-invoked recovery operation must preserve original bytes in a dated backup, validate a typed candidate and explicitly show changed/defaulted fields before replacement. A GUI form must not write arbitrary JSON or claim Save/Repair success while disconnected. Until that offline recovery executor exists, offer diagnostics/open location/retry and state the limitation; no inert Repair button. Resync version/revision before committing any retained Settings draft.

## Memory interface baseline (GUI-0d; implement in GUI-3/GUI-5)

Reuse existing `memories` storage, owner/project scope, `entity_version`, retention/sensitivity/provenance/evidence, expiry, supersession and soft deletion. Do not create a client JSON database or expose capture scratchpads. Missing creation/importance/relevance fields stay absent unless a deliberate migration with real provenance supplies them.

Proposed owner-local authenticated operations: bounded list/search; exact-ID detail; explicit version-checked correction; explicit forget; a bounded neighborhood/relation projection in GUI-5. Default list limit 50, maximum 100, validated filters and deterministic opaque cursor. Return exact memory IDs/revisions, actual supported public fields, available evidence references, next cursor and projection epoch. Unknown/deleted/cross-owner IDs must not select another record or leak private data. Concurrent edits yield typed conflicts plus current permitted revision; offline UI edits remain drafts.

Correction creates/links a canonical successor and updates retrieval semantics atomically; forget excludes the record from canonical retrieval and browser results as specified. Report restoration/audit limitations accurately; never promise deletion of backups or external agent transcripts. Existing capture rationale remains private and must not become a public evidence chip. GUI-3 finalises route names, public field redaction, mutation policy and migration/restore tests before exporting schema.

Relations use canonical source/target IDs, relation kind, evidence reference and version, scoped to the same permitted owner/project. No edges merely because nodes share a colour/position or an LLM said they are related. Neighborhood responses cap at 75 nodes and 300 edges and expose a truthful truncation indicator; no invented omitted count or score. Native graph has a list equivalent and selected ID shared with the inspector. Real supported relations must exist before the graph is called delivered.

## Automation interface baseline (GUI-0d; implement in GUI-4)

Canonical persistence lives in Core with schema migrations, not UI timers. Proposed definition fields: exact automation ID, owner/profile identity, entity version, name, bounded prompt/task specification, enabled/paused state, typed schedule/timezone and policy/tool requirements. UI drafts submit explicit expected versions; create/update/pause/resume/run-now remain separate operations. Pause affects future admission and never claims to cancel active work.

Bounded list/detail and paginated occurrence logs expose real definition/version/occurrence/task IDs, scheduled/admitted/finished times where known, statuses, outcomes and evidence links. Occurrences have a unique definition/scheduled-slot identity and durable task admission linkage. A versioned idempotency key for run-now prevents double-click/retry duplication. Reconcile admission and task persistence atomically where possible; unknown outcomes are not replayable successes/failures.

One-off, daily, weekly and interval schedules are in scope. GUI-4 must explicitly finalise IANA/Windows timezone conversion, DST gap/fold, missed-run bounds, overlap policy, fixed-interval clock/restart semantics and uncertain admission before implementation closure. Current GUI-0 does not select untested scheduling defaults. Dispatch through existing canonical task admission and static local policy; unavailable/disabled tools/providers produce visible failure/deferred outcomes, not hidden permission requests or direct user-file authoring. SORA can propose/edit supported automation definitions only through the final bounded policy-aware API, not write scheduler records freely.

## UI presentation request/ack baseline (GUI-0d; implement in GUI-3)

The model requests semantic actions over allowlisted panel/record identities, never arbitrary coordinates, HWNDs, paths or executable commands. Core derives authority and profile/host binding. A host-bound registry resolves current visible controls and their bounds only after canonical selection succeeds. Existing native control references and renderer POINT commands are reused at the presentation boundary; they are not interchangeable with memory/panel IDs.

Proposed request envelope: schema version, request ID, profile ID, host instance/epoch, panel enum, operation (`open`, `select`, `highlight`), optional exact canonical target ID/version, origin, permitted activation mode and expiry. Origin/activation rights are derived by Core, not caller assertions. Host deduplicates by request ID within bounded retention and acknowledges `opened`, `already-visible`, `selected`, `deferred`, `unavailable` or `rejected`, with target/host version and reason. Acknowledge success only after the panel/record actually exists and is selected; Chat success chips consume that acknowledgement, not mere dispatch.

User focus/drafts win. Ambient requests do not steal focus, reopen a dismissed/minimised panel from the same suggestion or discard edits. Unknown/deleted/stale targets clear highlight and return typed unavailable/conflict; they never select a nearby record. Topology/scroll/resize/DPI/control replacement revalidates anchors; target loss clears temporary emphasis/POINT. Reduced motion uses static emphasis. Gesture failure cannot invalidate a successful record selection or prove desktop effects. No automatic effect replay after reconnect; a new host epoch invalidates old registry bindings.
